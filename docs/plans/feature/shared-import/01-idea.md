# Idea

## Request

Add an import command that replaces a site's remote `shared/` directory from a
ZIP archive produced by `bonesdeploy site export` or built with the same
top-level `shared/` layout from a manually synchronized site directory.

## Problem

BonesDeploy can export persistent shared site data, but restoring or migrating
that data requires an operator to reproduce privileged extraction, ownership,
service-quiescence, replacement, and recovery steps manually. Extracting over a
live directory can mix old and new files, lose concurrent writes, expose unsafe
archive paths, or leave a partially restored site after failure.

## Definitions

**Shared import:** Replacement of every entry in the configured site's remote
`shared/` directory except `shared/.env` with the contents of an accepted ZIP
archive. It is replacement, not a merge: remote entries absent from the archive
do not survive.

**Accepted shared archive:** A valid ZIP whose entries are all rooted beneath
one top-level `shared/` directory. The archive may be produced by
`bonesdeploy site export` or independently with the same layout. It may contain
regular files, directories, and relative symbolic links that remain within
`shared/`. It does not carry trusted ownership, permissions, or site identity.

**Staged replacement:** A private temporary directory on the remote site's
filesystem into which an accepted shared archive is validated and extracted
before live data is changed. It is not a deployment release or persistent
backup.

**Cutover:** The brief interval in which site services are stopped, the current
environment file is carried into the staged replacement, and the staged and
live shared directories are atomically exchanged before services restart.

**Volatile application state:** Application-managed files in `shared/`, such as
Laravel file sessions, caches, compiled views, locks, queues, and logs. These
files have no framework-specific treatment during import and are replaced like
all other non-environment shared data.

## Desired outcome

`bonesdeploy site import <archive> [--yes]` validates and uploads an accepted
shared archive, obtains explicit confirmation, and replaces the configured
site's shared data through a typed privileged BonesRemote operation. The site
remains available while the archive is received and staged, stops only for
cutover, and returns to service against the imported data. The existing remote
`shared/.env` remains unchanged. Any failure before cutover leaves the live site
unchanged, and a failed restart restores the previous shared directory and
service operation.

## Scope

- Add the local `site import` command, archive argument, `--yes` automation
  option, destructive confirmation, transfer, and result reporting.
- Add a narrow BonesRemote shared-import command that validates the site,
  serializes site mutations, receives and defensively extracts ZIP input,
  preserves `shared/.env`, normalizes imported ownership and permissions,
  performs cutover, verifies service restart, and rolls back on failure.
- Accept archives generated by `site export` and structurally equivalent ZIPs
  created from a manually synchronized `/srv/sites/<site>/shared` directory.
- Serialize `secrets push` with shared import so preservation of the current
  environment file cannot race an environment update.
- Detect and recover an interrupted cutover before beginning another import so
  the previous shared directory is not silently abandoned.
- Add focused automated coverage and operator documentation, including the
  effects of restoring opaque volatile application state.

## Constraints

- Import replaces shared data; it does not merge archive entries into the live
  directory.
- The archive's `shared/.env` is ignored. The current remote `shared/.env`
  remains authoritative and `secrets push` remains its only content writer.
- A missing, non-regular, or unsafe live `shared/.env` blocks import with
  guidance to repair it through `bonesdeploy secrets push` or site setup.
- Archive paths, links, entry types, entry counts, expanded bytes, and available
  filesystem space are validated at the privileged extraction boundary before
  cutover.
- Site services must not write shared data during cutover and must restart so
  no process retains stale file handles.
- Imported data is owned by the site's runtime identity and cannot introduce
  special mode bits or world-accessible files through archive metadata.
- Existing deployment locking, canonical path derivation, SSH transfer policy,
  systemd lifecycle, and root privilege checks remain authoritative.
- Application data is opaque. Import does not run framework commands or infer
  which application files are disposable.
- E2E tests are not run as part of this change.

## Exclusions

- Borg archive restoration, database export or restoration, and consistency
  coordination with databases or object stores outside `shared/`.
- Merge mode, selective paths, path remapping, cross-site selection, archive
  editing, or retention of successful import history.
- Importing the archive's `.env`, changing local encrypted secrets, or
  reconciling imported application data with destination secrets.
- Framework-specific cache clearing, session preservation or invalidation,
  migrations, storage-link creation, or post-import hooks.
- Progress bars, encryption of the ZIP transport, and changes to the existing
  live best-effort export behavior.
